# 발행 성과 원장 기준

> 목적: 발행한 글이 실제로 검색에 붙었는지를 집계 가능한 형태로 남긴다. daily는 증거 로그라 산문으로 흩어져 있어 "이 전술이 먹히는가"를 판정할 수 없다.
> 원본: `data/performance/post_performance.json`
> 최종 업데이트: 2026-07-27

## 1. 왜 만드는가

2026-07-27 기준 Q-013·018·019·026·027·028·031 일곱 건이 모두 "정확 유입 미확인 → 확장 닫음"으로 종료됐다. 개별 글은 닫혔지만 **같은 전술이 일곱 번 실패했다는 사실은 어디에도 집계되지 않았다.** 그래서 다음 후보도 같은 방식으로 올라왔다.

이 원장은 개별 글의 성패가 아니라 **클러스터 단위 전술의 승률**을 보기 위한 것이다.

## 2. 관측 실패와 성과 실패를 구분한다

가장 중요한 설계 원칙이다.

daily에 TOP20 표가 없거나 행이 몇 개뿐인 날의 데이터로 "이 글은 검색에 안 붙었다"고 판정하면 안 된다. 실제로 2026-07-11~15는 TOP20 표가 아예 없고, 07-24~27은 작성일 열이 빠져 있다.

그래서 판정값에 `unobserved`를 둔다. **`unobserved`는 절대 `faded`로 승격하지 않는다.**

### 관측 유효일

아래를 모두 만족하는 날만 관측 유효일로 센다.

- 해당 daily에 `게시글 TOP` 표가 존재한다
- 표의 데이터 행이 5개 이상이다

## 3. 스키마

```json
{
  "schema_version": 1,
  "id": "post_performance",
  "updated_at": "YYYY-MM-DD",
  "posts": [
    {
      "post_no": "140",
      "title": "드레스룸 슬라이딩도어가 불편한 집은 이유가 있습니다",
      "published_at": "2026-07-08",
      "queue_id": "Q-005",
      "hub_ids": ["H4"],
      "cluster_ids": ["C-H4-SLIDING-ROOM"],
      "observations": [
        { "date": "2026-07-20", "day": 12, "rank": 3, "views": 30 }
      ],
      "observed_days": 8,
      "verdict": "landed",
      "verdict_at": "2026-07-27",
      "verdict_reason": "발행 3~14일 구간에 TOP20 6회 등장"
    }
  ],
  "unmapped_titles": [
    { "title": "...", "dates": ["2026-07-20"], "reason": "등록부에서 글번호를 찾지 못함" }
  ]
}
```

### 필드 규칙

| 필드 | 규칙 |
| --- | --- |
| `post_no` | 3자리 문자열. 등록부 기준 |
| `published_at` | 등록부 `발행일(TOP20 작성일 기준)`. 없으면 daily TOP20 표의 `작성일`로 보정 |
| `queue_id` / `hub_ids` / `cluster_ids` | `SEO_TAXONOMY.json`의 `post:NNN` 할당에서 가져온다. cutover(152) 이전 글은 빈 배열 허용 |
| `observations[].day` | `date - published_at` 일수 |
| `observations[].rank` / `views` | daily TOP20 표 값. 공동 순위는 표기된 값 그대로 |
| `observed_days` | 발행 후 0~14일 구간의 관측 유효일 수 |

## 4. 판정 규칙

발행 후 **3~14일 구간**만 본다. 발행 당일과 다음날은 신규 노출 효과가 섞이므로 제외한다.

| verdict | 조건 |
| --- | --- |
| `pending` | 발행 후 3일 미만 |
| `landed` | 3~14일 구간에 TOP20 등장 **2회 이상** |
| `faded` | 3~14일 구간 TOP20 등장 1회 이하 **그리고** `observed_days >= 5` |
| `unobserved` | 3~14일 구간 TOP20 등장 1회 이하 **그리고** `observed_days < 5` |

`unobserved`는 실패가 아니다. 관측을 못 한 것이다. 전술 승률 계산에서 분모에도 분자에도 넣지 않는다.

## 5. 클러스터 전술 판정

원장이 쌓이면 클러스터 단위로 집계한다.

```text
승률 = landed / (landed + faded)
```

| 상태 | 조건 | 처리 |
| --- | --- | --- |
| 정상 | 승률 40% 이상 | 유지 |
| 경고 | 같은 클러스터에서 `faded` 3연속 | `ops:weekly`에서 WARN. 다음 scorecard에 해당 클러스터 신규 후보를 올릴 때 분리 각도를 반드시 밝힌다 |
| 재설계 | 같은 클러스터에서 `faded` 5연속 | 해당 클러스터 신규 발행을 멈추고 전술을 다시 설계한다. 글감 후보로 올리면 BLOCK |

이 규칙의 목적은 개별 글을 벌주는 것이 아니라 **같은 실패를 다섯 번 반복하기 전에 멈추는 것**이다.

## 6. 앞으로의 daily 형식 고정

백필이 어려웠던 이유는 daily TOP20 표 형식이 일곱 가지로 갈렸기 때문이다. 앞으로는 아래로 고정한다.

```md
## 게시글 TOP20

| 순위 | 글번호 | 게시글 | 조회수 | 작성일 | 판단 |
| ---: | --- | --- | ---: | --- | --- |
```

`글번호` 열을 추가한다. 제목은 리라이팅으로 바뀌지만 글번호는 바뀌지 않는다. 이 열이 있으면 제목 매핑이 필요 없어진다.

`작성일` 열은 비우지 않는다. 발행 후 며칠차인지가 이 원장의 핵심 축이다.

## 7. 운영 명령

```powershell
npm run performance:collect   # 최신 daily에서 관측 추가
npm run performance:report    # 클러스터별 승률과 재설계 경고
```

`ops:weekly`에서 두 명령을 함께 호출한다.

## 8. 하지 않는 것

- 공감·댓글 수를 성과 판정에 넣지 않는다. 문제 공명 신호이지 검색 도달 지표가 아니다
- `ranking_report.md`의 순위 추적값을 이 원장에 섞지 않는다. weekly/experimental 자료다
- 관측이 부족한 구간을 추정값으로 메우지 않는다. `unobserved`로 남긴다
