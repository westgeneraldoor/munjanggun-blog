# 원고 작성 작업지시서

> 목적: 새 세션의 작업자가 문서 39개를 다 읽지 않고도 발행 가능한 원고 1편을 만들 수 있게 한다.
> 대상: 원고 작성만 담당하는 작업자 세션. 글감 선정과 전략 판단은 이 문서의 범위가 아니다.
> 최종 업데이트: 2026-07-27

## 0. 이 문서의 위치

문장군 블로그는 문서가 많다. 전부 읽으면 규칙이 섞여 판단이 흐려진다.
**원고 1편을 쓰는 작업이라면 이 문서와 아래 4개만 읽는다.**

| 순서 | 파일 | 왜 읽는가 |
| ---: | --- | --- |
| 1 | `posts/171_방문턱제거.md` | 레퍼런스 원고. 규칙 설명보다 이 파일이 먼저다 |
| 2 | `docs/operations/SINGLE_POST_FILE_STANDARD.md` 4-1절 | 승리 포맷 하드 기준 |
| 3 | `docs/strategy/POSTING_EXCLUSION_RULES.md` | 쓰면 안 되는 소재와 전환 방향 |
| 4 | `docs/strategy/POSTING_REGISTRY.md`의 `다룬 소재` 열 | 중복 확인. 전체를 읽지 말고 인접 번호만 본다 |

나머지 문서는 이 4개로 판단이 안 될 때만 연다.

## 1. 입력으로 받아야 하는 것

작업 지시에 아래가 없으면 **추측하지 말고 되묻는다.**

```text
원고 번호:
핵심 키워드:
고객 상황:
고객 불안/의심 문장:
중복 회피 대상 글 번호:
```

이 다섯 줄이 없는 상태로 쓰기 시작하면 기존 글과 겹치거나 검색되지 않는 글감이 나온다.

## 2. 작성 절차

### 2-1. 레퍼런스부터 읽는다

`posts/171_방문턱제거.md`를 연다. 규칙을 외우려 하지 말고 **문장의 리듬과 구체성**을 본다. 특히 아래 세 지점을 확인한다.

- 도입부에서 큰따옴표 대사가 나오는 위치
- 번호 소제목이 판단문으로 끝나는 방식
- 상담 전 준비 단락에 들어간 몸으로 하는 동작

### 2-2. 문장군이 할 수 있는 말인지 먼저 확인한다

키워드가 좋아도 취급 범위 밖이면 각도를 바꿔야 한다. 자주 걸리는 것만 정리하면 아래와 같다.

| 소재 | 처리 |
| --- | --- |
| 현관문, 방화문 | 영구 제외. 언급하지 않는다 |
| 비대칭양개형중문, 중문파티션 | 미취급. 가능 제품처럼 쓰지 않는다 |
| 9mm 문선 | 비교 검색어로만. 문장군 시공 서비스처럼 쓰지 않는다 |
| 문틀만 단독 교체 | 가능하다고 쓰면 FAIL. 문짝+문틀세트, 문짝교체+문선마감으로 전환 |
| 바닥 공사, 문턱 제거 | 문장군 단독 서비스로 쓰지 않는다. 원인 진단과 교체 범위 판단으로 전환 |
| 신발장리폼 | 제외 아님. 중문 현장의 간섭·추가금 변수로 사용 가능 |

가격, 리뷰 수, A/S 기간, 시공 일정, 성능 보장은 **본문에서 단정하지 않는다.** 중문 일정을 쓸 일이 있으면 `보통 3~6일 범위`로만 쓴다.

### 2-3. 구조를 이 순서로 만든다

```markdown
## 제목 후보 5개
1~5 (검색형·고객불안형·현장형·통념반박형·손실회피형 중 3가지 이상 섞기)

# 발행 제목

도입부 (고객 대사 큰따옴표 1회 포함)

## 1. 첫 번째 판단
## 2. 두 번째 판단
## 3. 세 번째 판단

## 실제 시공 현장에서는 조금 다릅니다

## 상담 전 이렇게 준비하면 좋습니다

## 관련 글

## 해시태그
```

`## 실제 시공 현장에서는 조금 다릅니다`는 **글자 하나도 바꾸지 않는다.** 다르게 쓰면 FAIL이다.

### 2-4. 수치 기준

| 항목 | 기준 |
| --- | --- |
| 본문 공백 제외 | 1,500~2,500자 |
| 제목 길이 | 24~40자 |
| 번호 판단 단락 | 3개 이상 |
| 고객 대사 | 큰따옴표 1회 이상 |
| 내부 링크 | 2개 이상 (실제 등록된 URL만) |
| 해시태그 | 5~10개, `#문장군` `#문장군중문` 필수, 띄어쓰기 금지 |

내부 링크는 **`POSTING_REGISTRY.md`에 URL이 등록된 글만** 쓴다. URL이 `-`인 글은 아직 발행 전이므로 링크하지 않는다.

### 2-5. 제목 패턴을 직전 글들과 겹치지 않게 한다

검사기가 제목을 `cost / compare / case / failure / criteria / other`로 분류한다. 최근 5편 중 같은 패턴이 3개를 넘으면 WARN이 뜬다. 작성 전에 확인한다.

```bash
node scripts/validate_post.js --all --no-write-report
```

## 3. 자가 검수

원고를 저장한 뒤 **반드시 직접 돌린다.** 사람에게 넘기기 전에 통과시킨다.

```bash
node scripts/validate_post.js posts/NNN_키워드.md --no-write-report
```

FAIL이 0이어야 한다. WARN은 아래만 무시해도 된다.

- `제목에 숫자가 없습니다` — TOP20 상위 글에도 숫자 없는 제목이 많다
- `098번 이후 현장형 원고는 본문 공백 제외...` — 1,500~2,500 범위 안이면 뜨지 않는다

나머지 WARN은 고친다.

### 검사기가 잡지 못하는 것

아래는 기계가 판정하지 못한다. **저장 전에 직접 눈으로 확인한다.**

- [ ] 번호 소제목만 읽어도 결론 3개가 잡히는가
- [ ] 각 번호 단락의 마지막 문장이 독자가 할 수 있는 행동이나 결론인가
- [ ] `~수 있습니다`로만 끝나는 문단이 연속되지 않는가
- [ ] 추상 명사(간격, 경계, 범위, 동선, 마감) 대신 사물 명사가 보이는가
- [ ] 현장 단락에 사건이 있는가. 확인 항목 나열로 끝나지 않았는가
- [ ] 상담 전 준비 단락에 몸으로 하는 동작이 하나 있는가

하나라도 아니면 `posts/171_방문턱제거.md`를 다시 열어 대조한다.

## 4. 하지 않는 것

- `posts/` 밖에 제작노트, 메모, 초안 파일을 만들지 않는다. 원고는 파일 하나다
- 본문에 `[사진:]`, `[AppSheet 확인]`, `[제작자 메모]`, `## 운영 메모`를 남기지 않는다. 남기면 FAIL이다
- 실제 고객 발언, 지역명, 아파트명, 수치를 근거 없이 지어내지 않는다. 현장 단락은 `비슷한 구축 아파트 현장에서도`처럼 일반화한다
- `POSTING_REGISTRY.json`, `ACTIVE_TOPIC_QUEUE.json`을 임의로 수정하지 않는다. 원고 작성과 원장 갱신은 다른 작업이다
- `posts/`를 커밋하지 않는다. `.gitignore`에 있으며 로컬 전용이다

## 5. 판단이 안 서면 멈춘다

아래 상황에서는 추측해서 진행하지 말고 **작업을 멈추고 보고한다.**

- 키워드가 취급 범위 안인지 애매할 때
- 기존 글과 각도가 충분히 갈리는지 확신이 없을 때
- 근거 없이 수치나 사례를 써야만 글이 완성될 것 같을 때
- FAIL이 남았는데 고치려면 규칙을 우회해야 할 때

문장군 블로그는 발행량보다 발행 안전성이 우선이다. 애매한 원고 1편보다 멈추고 묻는 편이 싸다.

## 6. 완료 보고 형식

```text
원고: posts/NNN_키워드.md
발행 제목:
본문 공백 제외: N자
번호 판단 단락: N개 / 고객 대사: N회
validate_post.js: fail 0 / warn N (내용)
중복 회피: NNN번과 __ 각도로 분리
근거 없이 쓰지 않은 것: (가격/일정/성능 중 해당 항목)
판단이 필요한 사항:
```
