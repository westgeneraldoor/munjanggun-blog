# ABS도어 하위 키워드 지도와 핵심 허브 순환 점검 설계

> 작성일: 2026-07-13
> 상태: 사용자 설계 승인 완료, 구현 전 검토용

## 1. 목적

`ABS도어`는 네이버 광고 API 시장 수요가 크고 문장군의 주요 서비스와 직접 연결되지만, 현재 운영 문서에는 허브 키워드로만 등록되어 있다. ABS도어 아래에서 어떤 고객 문제를 후속 글로 확장할지 구조가 약하고, 신규 글감 선정 때 핵심 허브 전체를 반드시 확인했다는 증거도 남지 않는다.

이번 변경의 목적은 다음 두 가지다.

1. ABS도어를 교체·문틀·가격·규격·사용 공간·종류·시공 판단으로 나눈 전용 하위 키워드 지도를 만든다.
2. 신규 글감 스코어카드마다 핵심 허브를 순환 점검하고, 누락이나 근거 없는 보류를 자동 경고한다.

ABS도어 글을 매번 강제 발행하지는 않는다. 최근 발행글, 작성완료·URL등록대기 글, 보호글과 가까우면 중복·카니발 방지를 우선하고 그 근거를 남긴다.

## 2. 권위와 적용 위치

운영 권위는 기존 체계를 유지한다.

- `docs/operations/TOPIC_SELECTION_SCORECARD.md`: 핵심 허브 순환 점검의 활성 규정
- `outputs/reports/topic_candidates/YYYY-MM-DD_topic_scorecard.md`: 매회 점검 결과가 남는 실행 증거
- `docs/strategy/ACTIVE_TOPIC_QUEUE.json`: 점검 결과의 다음 액션을 Q-ID로 닫는 실행판
- `docs/strategy/POSTING_REGISTRY.json`: 최근 글과 작성완료 글을 확인하는 중복·카니발 방지 원장
- `docs/strategy/SEO_KEYWORD_RESEARCH.md`: ABS도어 하위 키워드 구조를 설명하는 참고 지도
- `data/raw/keyword_data_product.json`: 검색량 숫자의 원본

`SEO_KEYWORD_RESEARCH.md`는 참고 문서이므로 순환 점검 계약을 단독으로 소유하지 않는다. 실제 계약은 `TOPIC_SELECTION_SCORECARD.md`와 검증 스크립트에 둔다.

## 3. ABS도어 하위 키워드 지도

ABS도어 허브 아래를 다음 의도군으로 나눈다.

| 의도군 | 대표 키워드 | 고객 질문 | 중복 회피 기준 |
| --- | --- | --- | --- |
| 교체 범위 | ABS도어교체, ABS문교체, ABS문짝 | 문짝만 바꿀 수 있는가 | 143번과 가까우면 새 글보다 관찰·내부링크 우선 |
| 문틀 상태 | ABS도어문틀, ABS문틀 | 문틀까지 같이 봐야 하는가 | 문틀만 단독 교체 가능 주장 금지 |
| 가격·견적 | ABS도어가격 | 왜 견적이 달라지는가 | 059번과 비용 각도가 겹치면 신규 가격글 보류 |
| 규격·실측 | ABS도어사이즈, ABS도어규격 | 기존 문짝 치수만 재면 되는가 | 셀프 제작 권유보다 무료 방문실측·주문제작·시공으로 전환 |
| 사용 공간 | 화장실ABS도어, 욕실ABS도어, ABS방문 | 습기 많은 공간에 어떤 범위를 봐야 하는가 | 화장실문·세탁실문 기존 글과 증상·공간 각도 분리 |
| 종류·선택 | ABS도어종류, 타공도어, ABS슬라이딩도어 | 민무늬·타공·슬라이딩 중 무엇이 맞는가 | 취급 가능한 제품과 구조만 설명 |
| 시공 판단 | ABS도어시공, ABS도어설치 | 현장에서 무엇을 확인하는가 | 가능 여부·시간·가격을 단정하지 않고 구조 변수로 설명 |

검색량은 원본 데이터의 조회일과 함께 표시한다. 문서에 숫자를 복사할 때는 `data/raw/keyword_data_product.meta.json`의 `data_date`와 일치시킨다.

## 4. 핵심 허브 순환 점검 계약

핵심 허브는 다음 다섯 개로 고정한다.

- 중문
- 3연동중문
- 현관중문
- 방문교체
- ABS도어

신규 글감 스코어카드에는 `## 핵심 허브 순환 점검` 섹션과 아래 열을 가진 Markdown 표를 둔다.

| 핵심 허브 | 상태 | 근거 글/Q-ID | 판단 근거 | 다음 액션 |
| --- | --- | --- | --- | --- |

허용 상태는 다음 네 가지다.

- `작성 후보`: 이번 후보 또는 가까운 차기 후보로 승격
- `보호`: 기존 성과 글을 유지하고 내부링크·제목 보정만 검토
- `관찰`: 최근 발행 또는 URL등록대기 글의 3일·7일 반응 확인
- `중복 보류`: 최근 글과 카니발 위험이 커 신규 글을 만들지 않음

모든 핵심 허브 행에는 근거 글 번호 또는 Q-ID가 필요하다. `중복 보류`와 `관찰`은 어떤 기존 글과 가까운지, 언제 다시 판단할지를 `판단 근거` 또는 `다음 액션`에 적는다.

이 표는 글감 3개 중 하나를 특정 허브로 강제하는 할당표가 아니다. 다섯 허브가 모두 검토됐고, 발행하지 않은 이유도 운영 증거로 남기기 위한 점검표다.

## 5. 자동 검증 동작

`scripts/validate_topic_scorecard.js`에 순환 점검 검증을 추가한다.

검증 결과는 이번 단계에서 하드 FAIL이 아니라 WARN으로 처리한다.

다음 조건에서 경고한다.

1. `핵심 허브 순환 점검` 섹션이 없음
2. 지정된 표 헤더가 없음
3. 다섯 핵심 허브 중 하나라도 행이 없음
4. 허용하지 않은 상태가 사용됨
5. 근거 글/Q-ID가 비어 있음
6. `관찰` 또는 `중복 보류`인데 재판단 근거·다음 액션이 없음

경고 메시지는 누락 허브와 실패 이유를 직접 표시한다. 예시는 다음과 같다.

```text
WARN: core hub rotation missing hub: ABS도어
WARN: ABS도어: 중복 보류 needs evidence post or Q-ID
```

`npm run ops:daily`는 이미 최신 topic scorecard 검증을 실행하므로 별도의 운영 명령을 추가하지 않는다. 기존 `--allow-missing=warn` 정책도 유지한다.

## 6. 테스트 설계

기존 topic scorecard 검증 테스트에 다음 사례를 추가한다.

1. 다섯 허브와 올바른 상태·근거·액션이 있으면 경고 없음
2. ABS도어 행이 빠지면 ABS도어 누락 경고
3. ABS도어가 `중복 보류`인데 글 번호나 Q-ID가 없으면 근거 부족 경고
4. ABS도어가 `관찰`이고 `143 / Q-006 / 3일 잔존 확인`이 있으면 허용
5. 알 수 없는 상태를 사용하면 상태 오류 경고
6. 기존 scorecard 파일은 순환 점검표가 없어도 하드 FAIL로 바뀌지 않음

## 9. 완료 기준

다음 조건을 모두 만족하면 구현 완료다.

1. ABS도어 하위 키워드 지도가 기존 H5 구조와 충돌 없이 문서화됨
2. 활성 주제 선정 규정에 핵심 허브 다섯 개와 순환 상태 계약이 명시됨
3. 최신 topic scorecard에서 다섯 허브의 판단을 확인할 수 있음
4. ABS도어 누락과 근거 없는 보류가 자동 WARN으로 검출됨
5. 정상적인 143번 관찰 상태는 경고 없이 허용됨
6. 관련 단위 테스트와 `npm run ops:daily`가 통과함
7. 기존 작업트리의 관련 없는 변경은 손상되지 않음
