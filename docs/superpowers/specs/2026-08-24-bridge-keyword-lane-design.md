# 문장군 브릿지 키워드 레인 설계

## 1. 목적

문장군 블로그는 약 200편을 발행하며 중문·방문·ABS도어 내부 키워드를 폭넓게 다뤘다. 앞으로의 신규 유입은 제품 키워드를 반복 재작성하는 방식이 아니라, 더 넓은 생활·공정·가구·주거 키워드에서 실제 문 시공 의사결정으로 이어지는 지점을 찾아야 한다.

브릿지 레인의 목적은 부모 키워드 목록을 제한하는 것이 아니다. 어떤 부모 키워드든 입력할 수 있게 두고, 그 키워드를 검색한 사람이 실제로 문·중문 때문에 순서, 마감, 반입, 원인, 일정, 예산, 계약 또는 생활 문제에서 막히는지를 검증한다.

## 2. 핵심 결정

### 2.1 부모 키워드는 개방형이다

`입주청소`, `타일`, `도배`, `마루`, `신발장`, `줄눈`, `씽크대`, `샷시`, `창호`, `이삿짐`, `이사일정`, `소파`, `침대`는 초기 탐색 예시일 뿐 허용 목록이 아니다. 새로운 생활 키워드는 설정 파일을 먼저 고치지 않아도 후보로 입력할 수 있어야 한다.

### 2.2 제품 레인과 브릿지 레인을 분리한다

기존 `topic:check`와 `config/product_scope.json`은 문장군 제품·서비스 안쪽의 안전성을 지키는 검사다. `타일`, `마루`, `창호` 등을 기존 `out_of_domain`에서 삭제하면 제품 전용 후보에 종합 인테리어 소재가 섞인다. 따라서 기존 제품 검사는 그대로 유지하고, 브릿지 전용 입력과 판정기를 별도로 둔다.

### 2.3 부모 단어가 아니라 연결 관계를 검사한다

브릿지 후보는 아래 다섯 필드를 갖는다.

- `parent_keyword`: 바깥 유입의 부모 키워드
- `service_keyword`: 문장군이 실제 취급하는 문·중문 서비스
- `relation_type`: 두 영역이 만나는 관계
- `customer_question`: 고객이 검색 직전에 할 법한 질문
- `dependency_statement`: 부모 검색자가 문 때문에 실제로 막히는 이유

예시:

```text
parent_keyword: 입주청소
service_keyword: 중문설치
relation_type: sequencing
customer_question: 입주청소를 먼저 하면 중문 설치 후 다시 청소해야 하나?
dependency_statement: 중문 설치 과정에서 발생하는 분진과 작업 동선 때문에 청소와 시공 순서를 함께 정해야 한다.
```

## 3. 연결 관계 분류

브릿지 레인은 다음 관계를 지원한다.

| relation_type | 의미 | 예시 |
| --- | --- | --- |
| `sequencing` | 공정 선후관계 | 입주청소 ↔ 중문 설치 |
| `finish_interface` | 서로 맞닿는 마감 경계 | 도배·타일·마루 ↔ 문틀·문선 |
| `clearance_logistics` | 반입 폭과 회전 동선 | 소파·침대·이삿짐 ↔ 문폭·중문 |
| `cause_diagnosis` | 불편의 원인을 제품별로 분리 | 샷시·창호 ↔ 외풍과 중문 효과 |
| `schedule` | 실측·제작·시공 일정 역산 | 이사일 ↔ 중문 시공 |
| `budget_priority` | 제한된 예산의 우선순위 | 신혼집·리모델링 ↔ 중문·방문 |
| `contract_responsibility` | 동의·원상복구·책임 범위 | 전세집 ↔ 문 교체 |
| `lifestyle_friction` | 생활 습관과 동선 문제 | 반려동물·육아·고령자 ↔ 문 구조 |

관계 종류는 제한된 어휘로 관리한다. 새로운 부모 키워드는 자유롭게 받을 수 있지만, 새로운 관계를 추가하려면 검증 규칙과 문서를 함께 바꿔야 한다.

## 4. 판정 규칙

### 4.1 자동 BLOCK

다음은 자동으로 막는다.

- `service_keyword`가 기존 문장군 제품 범위 검사에서 BLOCK인 경우
- 부모 키워드가 `excluded_permanent` 또는 `excluded_product`의 미취급 제품을 우회하는 경우
- `relation_type`이 등록된 관계 종류가 아닌 경우
- 고객 질문 또는 의존 문장이 비어 있는 경우
- 의존 문장에 문·중문 서비스 연결이 드러나지 않는 경우
- 등록부에 동일한 부모 키워드, 서비스, 고객 질문 조합이 이미 작성완료 상태로 존재하는 경우

### 4.2 WARN과 사람 검토

다음은 자동 승인하지 않고 WARN으로 보여준다.

- 처음 보는 부모 키워드
- 광고 API 데이터에 부모 키워드가 없는 경우
- 부모 키워드는 크지만 결합 질문의 검색 수요가 확인되지 않은 경우
- 등록부에 같은 부모 키워드 또는 같은 서비스의 근접 글이 있는 경우
- 법률, 하자 책임, 성능, 단열처럼 직접 근거가 필요한 관계

자동 검사는 하한선이다. 최종 승격 전 사람이 반드시 아래를 확인한다.

1. 부모 검색자가 실제로 문 때문에 결정에 막히는가
2. 글의 절반 이상이 부모 검색 의도에 답하면서도 문장군 서비스로 자연스럽게 좁혀지는가
3. 기존 글과 제목만 다른 같은 질문은 아닌가
4. 문장군이 종합 인테리어·가구·창호 업체처럼 읽히지 않는가
5. 실제 현장 사진이나 상담 장면으로 후매칭 가능한가

## 5. 데이터 구조

### 5.1 초기 시드 뱅크

`config/bridge_seed_keywords.json`은 허용 목록이 아니라 반복 수집용 기본 시드 뱅크다. CLI의 `--seeds` 인자로 언제든 다른 부모 키워드를 추가 조회할 수 있다.

초기 시드는 사용자가 제안한 다음 키워드로 시작한다.

```json
[
  "입주청소",
  "화장실타일공사",
  "도배",
  "마루",
  "신발장",
  "줄눈",
  "씽크대",
  "샷시",
  "창호",
  "이삿짐",
  "이사일정",
  "소파",
  "침대"
]
```

### 5.2 수집 산출물

- `data/raw/keyword_data_bridge.json`: 전체 연관 키워드와 원본 시드 연결
- `data/raw/keyword_data_bridge.meta.json`: 수집일, 시드, 행 수, 출처
- `data/raw/keyword_data_bridge.md`: 사람이 읽는 검색량 표

제품 데이터와 섞지 않으며 기존 `keyword_data_product*.json`을 덮어쓰지 않는다.

각 행은 다음 필드를 갖는다.

```json
{
  "keyword": "입주청소",
  "pc": 3360,
  "mobile": 70990,
  "total": 74350,
  "competition": "중간",
  "totalEstimated": false,
  "seedParents": ["입주청소"]
}
```

## 6. CLI 계약

### 6.1 부모 키워드 수집

```powershell
npm run keywords:bridge
npm run keywords:bridge -- --seeds "입주청소,소파,침대"
```

인자가 없으면 기본 시드 뱅크를 사용한다. `--seeds`가 있으면 그 실행에서는 지정된 시드만 조회한다. API 자격증명이 없으면 파일을 만들지 않고 종료 코드 1로 멈춘다.

### 6.2 브릿지 후보 검사

```powershell
npm run topic:bridge-check -- `
  --parent "입주청소" `
  --service "중문설치" `
  --relation "sequencing" `
  --question "입주청소를 먼저 하면 중문 설치 후 다시 청소해야 하나?" `
  --dependency "중문 설치의 분진과 작업 동선 때문에 청소 순서를 함께 정해야 한다."
```

출력은 부모 검색량, 서비스 취급 범위, 관계 유형, 부모 근접 글, 서비스 근접 글, 질문 근접 글, 자동 BLOCK/WARN, 사람이 확인할 항목을 구분한다.

## 7. 기존 시스템과의 관계

- `topic:check`: 제품 안쪽 신규 글감 검사로 유지한다.
- `topic:bridge-check`: 제품 밖 부모 키워드와 문장군 서비스의 연결을 검사한다.
- `product_scope.json`: 기존 제품 범위와 미취급 제품 차단을 유지한다.
- `bridge_keyword_policy.json`: 관계 종류와 알려진 부모 문맥 설명을 관리한다.
- `POSTING_REGISTRY.json`: URL 유무와 관계없이 브릿지 글도 작성완료 시 즉시 중복 방지 대상이 된다.
- `ACTIVE_TOPIC_QUEUE.json`: 브릿지 후보는 별도 lane과 Q-ID로 관리한다.

## 8. 201~207 코호트

201~207은 180~191 리라이팅 코호트에 포함하지 않는다. 브릿지 수집과 검증기를 구현한 뒤 전체 부모 후보를 경쟁시켜 일곱 개를 정한다.

선정 전에는 기존 글과 같은 질문을 제외한다. 현재 확인된 보호 대상은 다음과 같다.

- 도배·방문교체 순서: 165
- 이사 전후 중문 시점: 116
- 큰 가구·소파·침대 반입과 중문: 136
- 화장실 타일 경계와 문 교체: 007, 026, 053, 103
- 신발장 간섭: 025, 039 및 관련 다수
- 셀프중문 설치선: 200

브릿지 코호트의 성공 기준은 201번 발행 전에 별도 사전 등록한다. 8월 31일의 리라이팅 판정 기준과 모수는 바꾸지 않는다.

## 9. 비목표

- 종합 인테리어, 청소, 가구, 창호 서비스를 문장군 취급 서비스처럼 소개하지 않는다.
- 부모 키워드의 큰 검색량을 브릿지 글이 그대로 가져온다고 가정하지 않는다.
- 기존 글과 같은 질문을 부모 키워드만 바꿔 새 글로 만들지 않는다.
- 이번 구현에서 201~207 원고 본문을 작성하지 않는다.
- 네이버 관리자 통계, 고객 원본, AppSheet 원본을 공개 저장소에 추가하지 않는다.

## 10. 완료 조건

- 기존 제품 레인의 판정과 테스트가 변하지 않는다.
- 임의의 부모 키워드를 설정 변경 없이 수집·검사할 수 있다.
- 제품 서비스는 기존 범위 검사로 별도 검증된다.
- `입주박람회 + 중문` 같은 조합을 하나의 미취급 제품명으로 오판하지 않는다.
- `타일`, `마루`, `창호`, `소파` 같은 부모 키워드는 단독 문장군 서비스로 승격되지 않고 브릿지 문맥으로만 평가된다.
- 브릿지 후보가 기존 116·136·165 등과 겹칠 때 근접 글과 소재가 출력된다.
- 정식 전체 검증 `npm run validate`가 통과한다.
